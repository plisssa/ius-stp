# Research: Обработка обращений в СТП

**Feature**: [spec.md](./spec.md) · **Plan**: [plan.md](./plan.md) · **Date**: 2026-11-06

Фаза 0 плана. Для каждого неизвестного из Technical Context и каждой технологии: решение, обоснование, отвергнутые альтернативы. Стек (Python + FastAPI, PostgreSQL, веб-интерфейс, MCP-заглушки) утверждён студентом перед запуском плана.

## R1. Архитектурный стиль

- **Decision**: модульный монолит — одно веб-приложение и один фоновый обработчик (worker). Компоненты C-* из `docs/05-traceability.md` реализуются как модули с явными границами; ИИ-ассистент и MCP-серверы — отдельные процессы.
- **Rationale**: нагрузка до 500 заявок в сутки и 100 одновременных пользователей (НФТ-05); один разработчик; класс критичности business operational. Границы модулей сохраняют деление по C4 и позволяют вынести модуль в сервис позже. Ассистент вынесен в отдельный процесс, чтобы его отказ не влиял на ядро (P4) и чтобы его права ограничивались на уровне процесса (P5).
- **Alternatives considered**: микросервисы на каждый контейнер C4 — избыточная эксплуатационная сложность для объёма кейса; монолит без выделенных модулей — теряется трассируемость «требование → компонент» (P7).

## R2. Язык и веб-фреймворк

- **Decision**: Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2.0, Alembic.
- **Rationale**: утверждено студентом; OpenAPI-контракт генерируется из кода и сверяется с `contracts/http-api.yaml`; для ИИ-компонента и MCP в Python есть официальные SDK.
- **Alternatives considered**: Java/Spring — тяжелее для учебного прототипа; Node.js — нет преимуществ при Python-экосистеме ИИ.

## R3. Хранилище

- **Decision**: PostgreSQL 16 — единая БД ядра; схема `audit` для неизменяемой истории; отдельные роли БД для ядра, отчётов и MCP-серверов.
- **Rationale**: транзакции для смены статуса вместе с записью истории и события; `SELECT … FOR UPDATE SKIP LOCKED` для планировщика SLA; права на уровне ролей БД реализуют «только чтение» для MCP-серверов (P5); отчёты ФТ-27…29 — обычные SQL-запросы с индексами по дате и организации.
- **Alternatives considered**: отдельная аналитическая витрина — избыточна для трёх отчётов и 10 с на годовой отчёт; документная БД — сложнее транзакционная целостность истории.

## R4. Пользовательский интерфейс

- **Decision**: серверные шаблоны (Jinja2) с частичным обновлением страниц через HTMX; два интерфейса — портал клиента (C-PORTAL) и рабочее место (C-DESK).
- **Rationale**: один деплой, нет отдельной сборки фронтенда; достаточно для очереди с таймером SLA, карточки заявки и экрана «предложение ассистента → Утвердить / Изменить / Отклонить» (этап 2: макеты UI).
- **Alternatives considered**: SPA на React — даёт богаче UI, но удваивает объём работ и тестов; для прототипа не оправдано.

## R5. Таймеры SLA

- **Decision**: дедлайн и время предупреждения вычисляются и сохраняются при регистрации; фоновый worker каждые 30 с выбирает заявки с наступившим временем (`warn_at ≤ now`, `due_at ≤ now`) и обрабатывает их идемпотентно (флаги `warn_sent_at`, `breach_recorded_at`). Часы системы подменяемы для тестов.
- **Rationale**: погрешность ≤ 1 мин (НФТ-02) обеспечивается интервалом 30 с; после сбоя пропущенные события обрабатываются по сохранённым значениям, без повторов (P4, пограничный случай «сбой во время отсчёта»).
- **Alternatives considered**: таймеры в памяти процесса — теряются при перезапуске; исполнение BPMN-модели движком Camunda — точно повторяет модель, но добавляет движок и его эксплуатацию; оставлено как вариант для этапа 2.

## R6. Рабочее время и календарь (решение ASM-07)

- **Decision**: у организации поле `sla_hours_type` = `business` | `calendar` и часовой пояс. Для `business` — рабочие часы организации и производственный календарь РФ (таблица `production_calendar`, загружается на 2026–2027 годы из официального календаря); для `calendar` — 24/7. Правило «3 рабочих дня» (BR-19) всегда считается по производственному календарю.
- **Rationale**: соответствует решению Q2 = C на G3 и тексту кейса («время задаётся в SLA между организацией и СТП»). Изменение типа часов действует только на новые заявки.
- **Alternatives considered**: только рабочие или только календарные часы — отклонены на G3.

## R7. События между модулями (C-BUS)

- **Decision**: transactional outbox — событие записывается в таблицу `outbox` в той же транзакции, что и изменение заявки; worker доставляет события подписчикам (уведомления, SLA, ассистент) с повторными попытками.
- **Rationale**: гарантированная доставка уведомлений (EARS-07) без распределённых транзакций; явный контракт событий (`contracts/events.md`) — стыки системы описаны как артефакт (лекция 1.3).
- **Alternatives considered**: Kafka — оправдана при большом числе потребителей и объёмов, для кейса избыточна (остаётся путём роста); вызовы напрямую из кода — теряются события при сбое почты или Slack.

## R8. Уведомления

- **Decision**: два адаптера за общим интерфейсом: почта (SMTP) и Slack (incoming webhook). В прототипе — локальный SMTP-перехватчик (Mailpit) и заглушка webhook, пишущая в журнал.
- **Rationale**: каналы заданы кейсом (BR-12); заглушки позволяют проверять доставку в тестах и quickstart без реальных сервисов.
- **Alternatives considered**: только почта — противоречит кейсу.

## R9. ИИ-ассистент и harness

- **Decision**: отдельный процесс `assistant`: получает событие «заявка создана», вызывает языковую модель через провайдер-независимый интерфейс, обращается к данным только через MCP-клиент к трём MCP-серверам (`tickets`, `kb`, `staff`), результат — структурированный JSON, проверяемый по схеме, сохраняется через `proposal.save`. Модель для прототипа выбирается на этапе 2; для промышленной эксплуатации — модель, размещённая в РФ или в контуре компании (152-ФЗ).
- **Rationale**: N×M → N+M — ассистент и любые будущие агенты подключаются к одним и тем же MCP-серверам; провайдер-независимый интерфейс позволяет сменить модель без изменения ядра; структурированный вывод исключает «свободные» действия.
- **Alternatives considered**: прямой доступ ассистента к БД — нарушает P5; встраивание вызова модели в ядро — нарушает P4 (отказ модели влиял бы на регистрацию).

## R10. Guardrails и защита от prompt injection

- **Decision**: (1) allow-list инструментов проверяется на стороне MCP-сервера, а не только в промпте; (2) MCP-серверы работают под ролями БД «только чтение», кроме `proposal.save` с правом вставки в одну таблицу; (3) текст заявки передаётся модели в отдельном блоке недоверенных данных; (4) вывод модели проверяется JSON-схемой, рекомендованный исполнитель — по детерминированному фильтру компетенций; (5) тайм-аут 60 с и порог уверенности 0,6; (6) ПДн маскируются до вызова модели; (7) все вызовы инструментов журналируются.
- **Rationale**: защита не зависит от «послушности» модели (ИИ-06, ИИ-07, P5); набор из ≥ 20 сценариев внедрения инструкций — часть тестов.
- **Alternatives considered**: защита только инструкциями в промпте — недостаточна при prompt injection.

## R11. Аутентификация и доступ

- **Decision**: клиенты — учётные записи портала (хеш паролей argon2id, сессии с тайм-аутом); сотрудники СТП — корпоративный вход по OIDC в эксплуатации, локальные учётные записи в прототипе. Ролевая модель: Клиент, Инженер, Руководитель, Администратор; проверка принадлежности заявки организации на каждом запросе.
- **Rationale**: НФТ-06, НФТ-07; пограничный случай «чужая заявка по прямой ссылке».
- **Alternatives considered**: единая база учётных записей для клиентов и сотрудников — смешивает внешний и внутренний контуры.

## R12. Тестирование

- **Decision**: pytest; httpx-клиент FastAPI для API; подмена времени (time-machine) для SLA, 3 рабочих дней и 2 недель; контрактные тесты ответа API против `contracts/http-api.yaml`; набор тестов на prompt injection; критерии приёмки EARS — основа интеграционных тестов.
- **Rationale**: P7 — критерии приёмки превращаются в автотесты; все временные правила проверяются детерминированно.
- **Alternatives considered**: ручная проверка временных правил — невоспроизводима.

## R13. Надёжность и резервное копирование

- **Decision**: PostgreSQL с ежедневной полной копией и архивированием WAL не реже раза в час; восстановление на момент времени; класс критичности — business operational.
- **Rationale**: выполняет RPO ≤ 1 ч и RTO ≤ 2 ч из НФТ-01 в пределах ориентиров класса (лекция 1.3: «часы»). Заявки за последний час до сбоя восстанавливаются по уведомлениям на почту и в Slack (BR-12), поэтому более строгий RPO не окупает затрат.
- **Alternatives considered**: RPO ≤ 5 мин с повышением класса до business critical — требует сократить RTO до минут и держать резервную площадку, что не оправдано для внутреннего сервиса на 500 заявок в сутки (решение студента от 07.11.2026, вопрос G2).

## R14. Наблюдаемость

- **Decision**: структурированные журналы (JSON), метрики (Prometheus): число заявок, доля в SLA, задержка уведомлений, задержка и стоимость вызовов модели, доля принятых предложений; трассировка запросов (OpenTelemetry); журнал вызовов инструментов агента — в таблице `assistant_tool_call`.
- **Rationale**: НФТ-13, ИИ-10, ИИ-11, P6; эти метрики понадобятся для SLO/SLI на этапе 3.
- **Alternatives considered**: только текстовые журналы — нельзя посчитать SLI.

## Итог

Все пункты Technical Context определены; неразрешённых `NEEDS CLARIFICATION` нет.
