# 1. Анализ автоматизируемого процесса и обоснование нотации

Документ описывает процесс обработки обращений в службу технической поддержки (СТП): участников, бизнес-правила из текста кейса, жизненный цикл заявки, модель процесса, проблемы текущего процесса и допущения, а также обосновывает выбор нотации и программы для моделирования. Сведения, которых нет в тексте кейса, оформлены как допущения (раздел 1.8).

## 1.1. Объект автоматизации и границы

**Объект** — процесс обработки обращений клиентов в СТП компании-разработчика ПО: от поступления обращения через веб-портал до закрытия заявки.

**Клиенты** — сотрудники организаций, эксплуатирующих ПО. Новые клиенты задают вопросы по функционалу и конфигурации ПО. Давние клиенты сообщают об ошибках разной критичности и спрашивают о выходе версий с исправлениями.

**Границы системы (что внутри):** регистрация заявок, статусная модель, контроль SLA первого ответа, уведомления, назначение и эскалация, работа с заявкой, закрытие и возобновление, отчётность, журнал изменений.

**Вне границ (внешние системы):** корпоративная почта, корпоративный чат Slack, серверы клиентов с расширенной поддержкой (удалённый доступ), договоры SLA (источник нормативов).

**Верхнеуровневая цепочка (по кейсу — 3 этапа):**

```
[1. Создание заявки] → [2. Взаимодействие клиента и исполнителя] → [3. Закрытие заявки]
```

## 1.2. Участники и роли

| Роль | Кто это | Что делает в процессе |
|---|---|---|
| Клиент | Сотрудник организации-клиента | Создаёт заявку на портале, отвечает на запросы, применяет решение, даёт обратную связь, может возобновить заявку |
| Инженер ТП | Сотрудник СТП | Берёт заявку, проверяет приоритет и инсталляцию, диагностирует, запрашивает информацию, эскалирует, даёт решение, закрывает |
| Более опытный инженер | Инженер ТП более высокой квалификации | Получает заявку при эскалации |
| Руководитель подразделения ТП | Руководитель СТП | Назначает исполнителя при отсутствии свободных инженеров, получает уведомления о нарушении SLA |
| ИУС СТП | Проектируемая система | Регистрирует заявки, считает SLA, рассылает уведомления, ведёт статусы, строит отчёты |
| ИИ-ассистент | Компонент проектируемой системы (новая функция) | Только **предлагает**: тип обращения, оценку приоритета, исполнителя, черновик ответа |

## 1.4. Жизненный цикл заявки (статусная модель)

| Из состояния | Событие | В состояние | Основание |
|---|---|---|---|
| — | Клиент нажал «Send» | Waiting for support, Unassigned | BR-01, BR-04 |
| Waiting for support | Инженер опубликовал ответ или запрос информации | Waiting for customer | BR-16, BR-18 |
| Waiting for customer | Клиент ответил или сообщил «не помогло» | Waiting for support | BR-21, **ASM-03** |
| Waiting for customer | Решение помогло, клиент согласен закрыть | Closed (решено) | BR-22, **ASM-04** |
| Waiting for customer | 3 рабочих дня без реакции, инженер закрывает | Closed (нет ответа клиента) | BR-19, **ASM-04** |
| Closed | Клиент возобновил в течение 2 недель | Waiting for support | BR-20, **ASM-04** |
| Closed | Прошло 2 недели | Closed (окончательно) | BR-20 |

Названия статусов «Waiting for support» и «Waiting for customer» взяты из кейса. Названия и правила, помеченные ASM, в кейсе явно не заданы.

## 1.5. Модель процесса

Модель — `models/stp-process.bpmn` (BPMN 2.0; открывается в Camunda Modeler или на demo.bpmn.io). Это модель **целевого процесса** — того, как он будет работать с системой: шаги и правила кейса сохранены, добавлены дорожка системы и дорожка ИИ-ассистента.

**Дорожки:** Клиент · ИУС СТП · ИИ-ассистент · Инженер ТП · Руководитель ТП.

**Ключевые элементы (ID используются в трассируемости):**

| ID элемента | Тип BPMN | Название | Правила |
|---|---|---|---|
| T_Submit | user task | Заполнить заявку на портале и нажать «Send» | BR-01 |
| T_Register | service task | Зарегистрировать заявку | BR-02–04 |
| T_StartSLA | service task | Рассчитать дедлайн первого ответа по SLA | BR-07, BR-08 |
| ICE_Warn → T_Warn | timer + send task | За 1 ч до дедлайна — предупредить инженеров | BR-11 |
| ICE_Breach → T_Breach | timer + send task | Дедлайн истёк — зафиксировать нарушение, уведомить всех | BR-10 |
| ICE_FirstResp1/2 | signal catch | Первый ответ опубликован → SLA соблюдён | BR-09 |
| T_Notify | send task | Уведомить о новой заявке (e-mail, Slack) | BR-12 |
| T_AIProposal | service task | ИИ-ассистент: тип, приоритет, исполнитель, черновик | новая функция (1.7) |
| GW_Free | XOR | Есть свободный инженер? | BR-13 |
| T_Take / T_HeadAssign | user task | Взять заявку / Назначить инженера | BR-13 |
| T_Check | user task | Проверить приоритет и инсталляцию, рассмотреть проблему | BR-14, BR-21 (повторная диагностика) |
| GW_Competent → T_Escalate | XOR + user task | Хватает компетенции? / Эскалировать | BR-15, BR-06 |
| GW_Info, GW_Extended | XOR | Хватает данных? / Расширенная поддержка? | BR-16, BR-17 |
| T_RemoteDiag | user task | Собрать диагностику удалённо | BR-17 |
| T_RequestInfo / T_Answer | user task | Запросить информацию / Опубликовать решение | BR-16, BR-21 |
| T_RecordResponse + ITE_FirstResp | service task + signal throw | Зафиксировать ответ, статус Waiting for customer | BR-05, BR-09, BR-18 |
| T_ClientReview + BT_3days | user task + boundary timer | Изучить ответ / 3 рабочих дня без ответа | BR-19, BR-21 |
| GW_CloseNoReply | XOR | Закрыть по отсутствию ответа? («Нет» — ждать дальше) | BR-19: возможность, а не обязанность |
| GW_Solved | XOR | Вопрос решён? | BR-21, BR-22 |
| T_CloseDecision → T_Close | user + service task | Закрыть заявку с причиной | BR-22 |
| EBG_Reopen, ICE_Reopen, ICE_2weeks | event-based gateway + events | Возобновление в течение 2 недель | BR-20 |

Отчётность (BR-23) — отдельная функция, не входящая в поток заявки. Она описана в требованиях (ФТ-27…29).

## 1.6. Проблемы текущего процесса

| ID | Проблема | Следствие | Где в модели |
|---|---|---|---|
| P-01 | Назначение исполнителя не автоматизировано: заявку берёт тот, кто первым заметил | Задержка первого ответа, риск нарушения SLA в пиковые часы | GW_Free, T_Take |
| P-02 | При нехватке свободных инженеров решение принимает руководитель по неформализованным знаниям: занятость, компетенции, история с клиентом | Узкое место — руководитель; решения не воспроизводимы | T_HeadAssign |
| P-03 | Каждое событие уходит отдельным письмом и в Slack | Высокий шум оповещений; предупреждения SLA тонут в общем потоке | T_Notify |
| P-04 | Приоритет и инсталляцию указывает клиент, инженер перепроверяет каждую заявку вручную | Трудозатраты; спорный приоритет влияет на SLA | T_Check |
| P-05 | Эскалация — ручная смена исполнителя, в кейсе нет фиксации причины | Нет статистики по пробелам в компетенциях | T_Escalate |
| P-06 | Отчётность не автоматизирована (её требуется создать) | Нет данных для KPI процесса | ФТ-27…29 |

Каналы уведомлений (почта и Slack) заданы кейсом, поэтому они сохраняются. Остроту проблемы P-03 снижает то, что предупреждения о сроках SLA отправляются отдельными письмами (ФТ-19, ФТ-20) и видны в очереди заявок (ФТ-07).

## 1.7. Целевой процесс: что автоматизируется

1. **Система** берёт на себя всё, что в кейсе описано как правило: ID, статусы, таймеры SLA, уведомления, правила «3 рабочих дня» и «2 недели», отчёты, журнал.
2. **ИИ-ассистент** встраивается в шаги, где сейчас нужен человеческий анализ текста. Он **только предлагает**:
   - А1 — тип обращения (вопрос по функционалу / по конфигурации / ошибка / вопрос о версиях);
   - А2 — оценку соответствия приоритета описанию (флаг «возможно не соответствует» с обоснованием);
   - А3 — рекомендуемого исполнителя с учётом занятости, компетенций и истории работы с клиентом (то, на что сейчас опирается руководитель, BR-13);
   - А4 — черновик первого ответа или запроса диагностической информации.
3. **Распределение ролей:** ассистент предлагает, система выполняет правила, человек утверждает решения. Ассистент не отправляет ничего клиенту, не меняет приоритет, не назначает и не закрывает заявки и не имеет доступа к серверам клиентов.

## 1.8. Допущения

| ID | В кейсе не указано | Принятое допущение или решение |
|---|---|---|
| ASM-01 | Уровни приоритета и нормативы времени первого ответа | 4 уровня P1–P4; нормативы — параметр SLA каждой организации (в тестовых данных: 1 / 4 / 8 / 24 рабочих часа) |
| ASM-02 | Что делать с предупреждением «за час», если норматив ≤ 1 ч | Предупреждение отправляется сразу при регистрации |
| ASM-03 | Статус после ответа клиента | «Waiting for support» (следует из определения статуса в кейсе) |
| ASM-04 | Название статуса закрытия и статус после возобновления | «Closed» с причиной (решено / нет ответа клиента); при возобновлении — «Waiting for support», исполнитель сохраняется |
| ASM-05 | Что после ES-9999 (номер четырёхзначный) | **Решение:** после ES-9999 номер продолжается пятью и более цифрами (ES-10000) |
| ASM-06 | Кто именно закрывает заявку | Инженер-исполнитель |
| ASM-07 | SLA считается в рабочих или календарных часах; чей часовой пояс | **Решение:** тип часов (рабочие по производственному календарю РФ или календарные) задаётся в договоре SLA каждой организации; часовой пояс — организации-клиента |
| ASM-08 | Как измеряется «занятость» инженера | Число заявок исполнителя в статусе «Waiting for support» |
| ASM-09 | Кто такие «сотрудники, заявки от которых не были удовлетворены» (отчёт б) | **Решение:** сотрудники организаций-клиентов (авторы заявок), у которых за период есть заявка, не закрытая с причиной «решено» |
| ASM-10 | Адресаты предупреждения «за час» | Все инженеры ТП, как и для письма о нарушении |
| ASM-11 | Кто задаёт тип обращения | Клиент выбирает при создании, инженер может исправить; справочник из 4 типов взят из описания клиентов в кейсе |
| ASM-12 | Как определяется «более опытный инженер» | Атрибут «уровень квалификации» в справочнике инженеров (L1–L3) |

## 1.9. Обоснование выбора нотации

Процесс СТП **событийный**: таймер SLA, предупреждение за час, 3 рабочих дня, окно в 2 недели, уведомления по каждому событию. Отсюда главный критерий: нотация должна выражать время и события, а не только последовательность работ.

| Критерий | BPMN 2.0 | eEPC (ARIS) | IDEF0 | UML Activity |
|---|---|---|---|---|
| Таймеры (SLA, 3 дня, 2 недели) | ✅ timer events, в том числе граничные | ⚠️ только текстом в событии | ❌ нет времени | ✅ accept time event |
| Несколько участников | ✅ пулы и дорожки | ✅ орг. единицы у функций | ⚠️ механизмы | ✅ дорожки |
| Ветвление «что наступит раньше» | ✅ event-based gateway | ❌ | ❌ | ⚠️ через interruptible region |
| Сообщения и сигналы | ✅ | ❌ | ❌ | ✅ |
| Понятность бизнес-заказчику | ✅ | ✅ | ⚠️ | ⚠️ ближе к разработчикам |
| Стандарт и обмен моделями | ✅ ISO/IEC 19510, XML | ⚠️ проприетарный ARIS | ✅ IEEE 1320.1 | ✅ ISO/IEC 19505, XMI |
| Обработка программами (нужна для SDD) | ✅ текстовый XML | ❌ | ❌ | ⚠️ XMI громоздкий |

**Вывод:** BPMN 2.0. Только в нём три ключевых правила кейса (BR-08…11, BR-19, BR-20) выражаются стандартными элементами, а не комментариями. IDEF0 подходит для функциональной декомпозиции, но не для процесса с таймерами. Модель процесса дополнена диаграммой вариантов использования UML (раздел 1.11).

## 1.11. Диаграмма вариантов использования (UML)

| ID | Вариант использования | Участник | Требования spec |
