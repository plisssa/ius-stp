# Конституция проекта «ИУС СТП» (вариант 12)

## Основные принципы (Core Principles)

### P1. Спецификация — единый источник истины

- Любое изменение поведения системы ДОЛЖНО начинаться с изменения спецификации (`spec.md`), а не кода или модели.
- Требования, модели (BPMN, UML, C4) и задачи ДОЛЖНЫ храниться в репозитории и версионироваться.
- ЗАПРЕЩЕНО реализовывать поведение, которого нет в спецификации.

**Проверка:** у каждой задачи в `tasks.md` есть ссылка на требование (EARS-xx / ФТ-xx / НФТ-xx / ИИ-xx).

### P2. Модель предлагает · ядро исполняет · человек утверждает

- ИИ-ассистент ДОЛЖЕН только формировать предложения (уровень «черновик + human-gate»).
- Отправка сообщений клиенту, назначение исполнителя, изменение приоритета, типа и статуса, закрытие заявки ДОЛЖНЫ выполняться детерминированным ядром и только после действия человека.
- ЗАПРЕЩЕНО давать агенту права на запись в поля заявки, кроме поля «предложение ассистента».

**Проверка:** для каждого действия агента в плане указан уровень полномочий и точка human-gate.

### P3. Предметная область неизменна

- Процессы, роли, статусы («Waiting for support», «Waiting for customer»), документы и отчётность ДОЛЖНЫ соответствовать кейсу 12.
- Современные технологии (ИИ, MCP, SDD) применяются только к контуру выполнения и интеграции.
- Всё, чего нет в кейсе, ДОЛЖНО оформляться как допущение (ASM-xx) и согласовываться, а не вводиться молча.

**Проверка:** каждое правило в спецификации ссылается на BR-xx или ASM-xx.

### P4. Детерминированный SLA-контур и деградация без потерь

- Дедлайны, предупреждения, фиксация нарушений SLA, уведомления и статусы ДОЛЖНЫ вычисляться детерминированно, без участия модели.
- Дедлайн ДОЛЖЕН сохраняться при регистрации; таймеры ДОЛЖНЫ восстанавливаться после сбоя по сохранённому дедлайну.
- При недоступности ИИ система ДОЛЖНА продолжать работу по процессу кейса без ассистента.

**Проверка:** в `plan.md` SLA-компонент не имеет зависимостей от ИИ-компонента; есть тест отключения ассистента (EARS-15).

### P5. Zero trust для агента

- Агент ДОЛЖЕН получать доступ к данным и действиям только через MCP-серверы из allow-list с минимально необходимыми правами.
- Текст заявок, переписка и вложения ДОЛЖНЫ считаться недоверенными данными; инструкции в них ЗАПРЕЩЕНО исполнять.
- ЗАПРЕЩЕН доступ агента к серверам клиентов, учётным данным и данным других организаций.
- Персональные данные ДОЛЖНЫ маскироваться до передачи в модель.

**Проверка:** в плане есть перечень инструментов с правами; в задачах есть тесты на prompt injection (ИИ-07).

### P6. Наблюдаемость и аудит

- Каждое изменение заявки ДОЛЖНО попадать в неизменяемую историю (кто, когда, что, причина).
- Каждый вызов инструмента агентом и каждое решение человека по предложению ДОЛЖНЫ журналироваться.
- Каждое действие ИИ-агента над проектными артефактами ДОЛЖНО фиксироваться в `journal/agent-log.md` с указанием human-gate.

**Проверка:** в плане есть журнал tool-calls и метрики ИИ-10; журнал проекта ведётся.

### P7. Проверяемость и трассируемость

- Каждое ключевое требование ДОЛЖНО быть записано в EARS и иметь критерий приёмки.
- ДОЛЖНА поддерживаться матрица «требование → элемент BPMN-модели → элемент архитектуры».
- РЕКОМЕНДУЕТСЯ формулировать критерии приёмки так, чтобы их можно было превратить в автотесты.

**Проверка:** в матрице трассируемости нет требований без элемента процесса и без компонента.

## Дополнительные ограничения (Additional Constraints)

- Класс критичности системы — business operational (НФТ-01).
- Интеграции «система ↔ система» — через API и события; «агент ↔ система» — через MCP (N×M → N+M).
- Персональные данные клиентов хранятся в РФ (152-ФЗ).
- Названия статусов и формат идентификатора ES-NNNN не меняются без согласования с преподавателем.

## Порядок работы (Development Workflow)

1. Specify → **human-gate** (проверка `spec.md`) → Plan → **human-gate** (проверка `plan.md`) → Tasks → **human-gate** (проверка `tasks.md` и трассируемости).
2. Переход к следующему шагу — только после утверждения предыдущего артефакта человеком.
3. Внешний human-gate этапа — рецензия преподавателя на спецификацию.

## Управление (Governance)

- Конституция имеет приоритет над spec, plan и tasks. При конфликте исправляется нижестоящий артефакт.
- Изменение конституции — только через human-gate с записью в журнале и повышением версии (семантическое версионирование).
